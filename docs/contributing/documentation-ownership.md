# Documentation ownership and freshness policy

This page defines who is accountable for each documentation area and what
triggers a review, so contributors know which docs to update alongside a code
or process change. It complements the deterministic gates in
[Documentation quality suite](../testing/documentation-quality.md), which
catches the mechanically checkable parts of freshness (stale generated
artifacts, broken links, invalid examples, undated maturity claims); the rules
below cover the parts that require human judgment.

## Ownership and freshness by area

| Area | Canonical source | Owner (reviewer of record) | Freshness trigger |
|---|---|---|---|
| Configuration reference | [`config.schema.json`](../../config.schema.json), generated by `tools/Aws2Azure.ConfigSchema` | Whoever changes `Aws2Azure.Core.Configuration` contract types | Regenerate (`dotnet run --project tools/Aws2Azure.ConfigSchema`) in the same PR as any config-contract change; the `Generated_schema_matches_committed_artifact` and `Generated_configuration_reference_matches_committed_artifact` unit tests fail the build otherwise. |
| Configuration examples | [`docs/configuration/examples/*.json`](../configuration/examples/) | Whoever adds/changes a backend `kind` or `auth.mode` | Add or update the matching example in the same PR; `tools/Aws2Azure.DocsQuality` validates every example against `config.schema.json` on every PR touching docs. |
| Workload/certification docs | [`docs/site/workload-ga.json`](../site/workload-ga.json), `docs/workloads/*.yaml`, `docs/workloads/*.md` | The workload profile's designated qualification owner (see `docs/workloads/qualification/README.md`) | Regenerate whenever `docs/workloads/*.yaml` changes or a new qualification/evidence artifact is committed (`gap-docs` workflow enforces the regenerate-and-diff check); any hand-authored claim about a profile's maturity must cite the live verdict (`tools/Aws2Azure.DocsEval`'s maturity-claim scan enforces this). |
| Gap docs / operation reference | [`docs/gaps/<service>/<Operation>.yaml`](../gaps/README.md), generated `docs/site/**` | The service module owner making the capability change | Update the YAML in the same PR as the code change; `gap-docs` workflow validates schema and regenerates `docs/site/**`/`CapabilityRegistry.g.cs`, failing on any diff. |
| Release notes | [`docs/releases/*.md`](../releases/) | The release owner cutting the version | **Append-only.** Never edit a published release's historical claims for accuracy after the fact — corrections go in a dated errata section appended to that release's page (or a follow-up release note), never a silent rewrite. This preserves the historical-vs-live precedence rule documented in `documentation-manifest.json`. |
| Deployment docs | [`docs/deployment/*.md`](../deployment/) | Whoever changes deployment topology, the module-selection build graph, or the production runbook | Review whenever the referenced Bicep/deployment templates, `docker-compose.yml`, or startup validation behavior changes; these docs are in scope for `tools/Aws2Azure.DocsQuality`'s command/config snippet checks. |
| Operational docs (troubleshooting, SLO/operational qualification, RC canary, real-Azure validation) | [`docs/testing/*.md`](../testing/), [`docs/troubleshooting.md`](../troubleshooting.md) | Whoever changes the referenced workflow, classifier, or qualification contract | Review whenever the corresponding `.github/workflows/*.yml` or `tools/Aws2Azure.GapDocs` qualification logic changes; keep worked examples (YAML shapes, CLI invocations) in sync — `tools/Aws2Azure.DocsQuality` structurally verifies every referenced command path. |
| ADRs | [`docs/adr/*.md`](../adr/) | Whoever proposes the decision | Immutable once accepted; a reversal is a new ADR that supersedes the old one, never a hand-edit of the original decision. |
| Explanatory guides (getting started, adoption, azure-authentication, presigned-urls, versioning) | `docs/*.md` | Whoever changes the described behavior | Review whenever the described behavior, environment variable, or CLI flag changes; internal links and anchors are enforced by the `documentation` workflow's strict MkDocs build and `validate_docs_site.py`. |

## Precedence when documentation disagrees

`documentation-manifest.json`'s `authority_precedence` (generated by
`tools/Aws2Azure.Documentation`) states the canonical order:
live workload certification → workload profile manifests → gap docs → release
notes → explanatory guides. When a hand-authored guide and a live/generated
artifact disagree, the live/generated artifact is authoritative and the guide
is stale — file or fix it, do not assume the guide is right.

## What is (and isn't) mechanically enforced

Mechanically enforced today (see
[Documentation quality suite](../testing/documentation-quality.md)):

- Internal links and anchors resolve (MkDocs `--strict` plus
  `.github/scripts/validate_docs_site.py`).
- `docs/site/**` and `src/Aws2Azure.Core/Generated/CapabilityRegistry.g.cs` are
  never stale relative to their YAML/schema sources (`gap-docs` workflow).
- `config.schema.json` and `docs/configuration-reference.md` are never stale
  relative to the configuration contract types (unit tests).
- `llms.txt` and `documentation-manifest.json` are never stale relative to the
  documentation tree (`documentation` workflow's `--check`).
- Every committed configuration example, and every fenced JSON/JSONC snippet
  that looks like a full config document, validates against
  `config.schema.json` (`tools/Aws2Azure.DocsQuality`).
- Every `dotnet run --project`/`dotnet test`/`dotnet publish` command and every
  `eng/`/`.github/scripts/` script path referenced in a fenced shell snippet
  points at a path that actually exists (`tools/Aws2Azure.DocsQuality`).
- Uncited, unhedged maturity claims ("GA", "production-ready", "generally
  available") anywhere under `docs/` or in `README.md`
  (`tools/Aws2Azure.DocsEval`).

Not mechanically enforced — these rely on the ownership table above and PR
review, using the
[documentation review checklist](documentation-review-checklist.md):

- Whether a guide's *prose* still accurately describes current behavior (link
  validity and schema validity do not prove semantic accuracy).
- The append-only release-notes convention.
- ADR immutability.
- Whether a new workload/qualification concept needs a new adversarial case in
  `tools/Aws2Azure.DocsEval`'s dataset.
