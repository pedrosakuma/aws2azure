## Interpretation limits and promotion decision

These are passes against the committed absolute thresholds, **not evidence
of performance parity**. The real-Azure RC observation scenarios in
`tests/Aws2Azure.IntegrationTests` (`SecretsManagerRealAzureRcObservationTests`,
`DynamoDbRealAzureRcObservationTests`, and `S3RealAzureRcObservationTests`)
recorded the following `representative-load-throughput` metric values.
These are observation-harness measurements, not `Aws2Azure.PerfTests`
benchmark results or new performance baselines:

| Profile / run | Candidate | Prior | Policy floor |
|---|---:|---:|---:|
| `secretsmanager-basic-lifecycle` / `36455379008` | 5.882 | 5.182 | 4.5 |
| `dynamodb-basic-crud` / `36463787285` | 22.683 | 165.321 | 17 |
| `s3-basic-object-crud` / `36473482616` | 53.348 | 75.416 | 30 |

Values are the harness's `throughput_per_sec`, rounded here; exact values are
in the immutable evidence. The historical DynamoDB and S3 differences do not
establish a code regression: runner/backend conditions differed. The subsequent
controlled DynamoDB result below did not reproduce its large difference;
S3 still needs its own comparison. Neither result establishes equivalence or
a new baseline. No thresholds or policies were changed.
SecretsManager passes the existing 4.5 override, not the qualification floor
of 9; this does not settle the historical floor/authentication questions in
[#1016](https://github.com/pedrosakuma/aws2azure/issues/1016).

Before any stable decision, review these caveats and revalidate current
readiness, qualification freshness, exact artifacts, and observation freshness.

This record does not freeze eligibility at the time of consolidation.

## Offline investigation conclusions (2026-10-01)

### SecretsManager: concurrency question answered, floor not recalibrated

The complete controlled result is
[36875986895/1](https://github.com/pedrosakuma/aws2azure/actions/runs/36875986895),
using harness `1b1f73ce4acbb9bbd252333ceed5f48e24d5377f` and the unchanged
sealed RC5 runtime. Artifact `11173696246` has verified ZIP SHA-256
`a33e359acb5032495385f8777f3ce9348b85286be58299efbf09d4d04094634a`.
Its `report.json` is explicitly `promotable: false`.

The real-Azure scenario is
`SecretsManagerRealAzureConcurrencyTests.Exact_sealed_candidate_compares_five_and_eight_workers_on_one_backend`
in `tests/Aws2Azure.IntegrationTests/SecretsManager/`, not a PerfTests benchmark.
One runner/vault/configuration and one exact binary executed 5/8/8/5 workers,
followed by the separate 5/5 control. All six slots and twelve phases completed
with zero recorded operation errors/throttles. Recomputing from measurement
`lifecycle` rows, counting each row only once and dividing summed successful
logical reads by summed actual workload-plus-drain seconds, gives:

| Comparison | Logical GetSecretValue/s or ratio |
|---|---:|
| 5 workers, pooled first/fourth slots | 5.4410/s |
| 8 workers, pooled second/third slots | 8.7988/s |
| Pooled 8/5 | 1.6171 |
| Forward / reverse 8/5 | 1.6016 / 1.6329 |
| Separate 5/5 control, second/first | 0.99992 |

This supports near-proportional within-run scaling against the 1.6 worker-count
ratio, **not a requirement that five workers exceed nine reads/s**. The rate is
logical AWS-client lifecycle work, including consistency polling and SDK retries,
not physical Key Vault GET capacity. Qualification uses eight workers and
different stale-read polling from the five-worker observation. Neither an
extrapolation nor the eight-worker arm calibrates that observation's floor.
Earlier partial runs are not pooled into these results.

**Corrected rationale for #1016:** the historical explanation that concurrent
cohorts on one runner necessarily halve throughput is not supported for the
split-runner observations. Runner contention is not an established cause of
the current absolute rate. Keep 4.5 as the unchanged reviewed observation
override pending an explicit calibration decision; this diagnostic neither
revalidates 4.5 as a general capacity guarantee nor justifies replacing it
with 9. The nine-action serial lifecycle and worker count matter; completing
this concurrency comparison is not a reason to repeat SecretsManager.

This explanation supersedes the contention claim for this investigation.
The historical policy file
`docs/workloads/observation/secretsmanager-basic-lifecycle.yaml` still contains
that old claim. It is deliberately not rewritten by this explanatory review:
its exact bytes are bound into observation evidence through
`observation_policy_digest`. A future reviewed policy-text correction must
acknowledge that new digest; never rewrite retained bindings or regenerate old
captures to make them look like fresh evidence. No numeric floor, load shape,
policy, ledger or certification timestamp changes here.

The Actions run remains **failed** because automatic teardown reused an expired
Azure CLI assertion (`AADSTS700024`), not because measurement failed. Manual
cleanup and resource absence were recorded in #1016; #1073 subsequently fixed
cleanup reauthentication. That does not change the run conclusion or justify
rerunning the experiment. Historical workload authorization-failure causality
remains unproven; absence of recurrence is not a demonstrated auth fix.

### DynamoDB conclusion does not settle S3

[36637714583/1](https://github.com/pedrosakuma/aws2azure/actions/runs/36637714583)
used `DynamoDbRealAzureCrossoverTests.Exact_sealed_ABBA_and_AA_share_one_runner_and_backend`
against real Azure with the exact candidate/prior, one runner/backend,
eight workers, and prior/candidate/candidate/prior plus prior/prior control.
The retained #1062 result was candidate 110.624 versus prior 110.244
GetItem/s (mean ABBA rates, +0.345%), with A/A drift -0.240%. The historical
22.683 versus 165.321/s separation did not recur. This is evidence against a
large repeatable binary-specific slowdown under those conditions, not proof
of geography as the original cause, statistical equivalence, or long-run parity.

S3's 53.348 versus 75.416/s observation remains confounded by distinct runners
and storage backends; the old cohort archives (`10996372825` / `10996827836`)
have no operation-timing sidecars. The concrete remaining question is whether
that separation persists with the same runner/backend and counterbalanced
sealed runtimes. The [minimal S3 diagnostic](../testing/rc-staging-canary.md#controlled-s3-crossover)
was subsequently executed with authorization after the preflight fix in #1076.
[36941305177/1](https://github.com/pedrosakuma/aws2azure/actions/runs/36941305177)
used `S3RealAzureCrossoverTests` against real Azure on one runner/backend with
the sealed pair and ABBA plus prior/prior control. Pooled GetObject rates were
candidate 41.122320 versus prior 40.561928/s (+1.38157%); A/A second/first was
0.996454837 (-0.35452%). The historical roughly -29% deficit did not recur.
These diagnostic rates are not canonical qualification, equivalence proof,
or an explanation of the original difference.

All six slots/twelve phases passed with zero recorded errors/throttles.
Retain the quiet-period caveat: four requested 30-second waits measured slightly
short (maximum shortfall 1.0362 ms). No tolerance or artifact was rewritten.
The full result, artifact digest and independently verified resource cleanup
are recorded in [#1062](https://github.com/pedrosakuma/aws2azure/issues/1062#issuecomment-5943191098).
