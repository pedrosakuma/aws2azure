## Interpretation limits and promotion decision

These are passes against the committed absolute thresholds, **not evidence
of performance parity**. The real-Azure RC observation scenarios in
`tests/Aws2Azure.IntegrationTests` (`SecretsManagerRealAzureRcObservationTests`,
`DynamoDbRealAzureRcObservationTests`, and `S3RealAzureRcObservationTests`)
recorded the following `representative-load-throughput` metric values.
These are observation-harness measurements, not `Aws2Azure.PerfTests`
benchmark results or new performance baselines:

| Profile / run | Candidate | Prior | Policy floor |
|---|---:|---:|---:|
| `secretsmanager-basic-lifecycle` / `36455379008` | 5.882 | 5.182 | 4.5 |
| `dynamodb-basic-crud` / `36463787285` | 22.683 | 165.321 | 17 |
| `s3-basic-object-crud` / `36473482616` | 53.348 | 75.416 | 30 |

Values are the harness's `throughput_per_sec`, rounded here; exact values are
in the immutable evidence. DynamoDB and S3 differences remain unexplained.
Do not claim a code regression, equivalence, or a new baseline without
equivalent-condition investigation. No thresholds or policies were changed.
SecretsManager passes the existing 4.5 override, not the qualification floor
of 9; this does not settle the historical floor/authentication questions in
[#1016](https://github.com/pedrosakuma/aws2azure/issues/1016).

Before any stable decision, review these caveats and revalidate current
readiness, qualification freshness, exact artifacts, and observation freshness.
Observation evidence has a 72-hour limit measured from the window end; the
earliest observation boundary is SQS at `2026-10-01T14:10:59.5815164Z`.
Qualification has its own, earlier expiration: the SQS approval expires at
`2026-09-29T23:56:59.1385758Z`. Artifact retention does not extend either limit.
This record does not freeze eligibility at the time of consolidation.

No stable promotion workflow, stable/latest alias, or GitHub Release was
created by this consolidation. A separately reviewed promotion/readiness plan
and explicit promotion authorization remain outstanding.

## Reproduction

Follow the immutable download and identity construction steps in
[the RC runbook](../testing/rc-staging-canary.md) and the read-only portion of
`release-candidate-promote.yml`. Select artifacts by numeric ID, check successful
producer attempts and API upload digests, and verify downloaded ZIP checksums.
Download each evidence artifact selected by its receipt, then rerun:

```bash
dotnet run --project tools/Aws2Azure.GapDocs -c Release -- \
  validate-rc-observation \
  --evidence <profile>/observation.yaml \
  --binding <profile>/binding.json \
  --expected-evidence-digest <receipt-evidence-digest>
```

Reproduce the identity from the exact archive/GHCR interface documents. Inside
the extracted archive bundle, finalize using all four unmodified selection
receipts:

```bash
python3 eng/release-candidate-manifest.py finalize \
  <archive-root>/release-candidate-identity.json \
  <archive-root>/release-candidate-manifest.json \
  --observation <sqs-selection>/observation-upload-identity.json \
  --observation <secrets-selection>/observation-upload-identity.json \
  --observation <dynamodb-selection>/observation-upload-identity.json \
  --observation <s3-selection>/observation-upload-identity.json
```

Compare the generated bytes to `docs/releases/v1.1.1-rc.5-manifest.json`.
The generator validates the referenced archive members and executables relative
to the output directory. The committed manifest is a review copy; binaries
are intentionally not committed beside it. Do not validate it in isolation
without restoring that exact bundle layout. The identity must remain unchanged
when observations are added; only the final manifest content digest changes.
